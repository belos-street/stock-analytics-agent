# Documentation Writing Guidelines

个人编码习惯 - 技术教学文档编写规范

技术教学文档（含代码示例的 markdown 教程）的最终验收标准：**面试能答、功能能做**。编写时对照以下六维框架、可溯源原则与自查清单。

## 六维写作框架

### 1. 格式规范性

- 文件命名遵循 `XX-模块名.md` 规范
- 头部元信息完整（模块映射、预计时间、面试可答性）
- 所有代码块带语言标记（如 ```js ）
- 练习环节包含「要求 + 提示 + 预期效果」三段
- 面试回答模板使用 `> **问：**` 格式
- 技术绘图统一使用 Mermaid，禁止外链图片（目录树、UI 位置示意等属合法例外）
- 关键位置附「参考链接」：版本断言、关键 API、新特性/迁移点处附官方文档或 Release Notes（来源分级：官方域名 > GitHub changelog > 官方博客）
- 保证跨文档一致性：术语、版本号、归类、结论在全部文档间保持一致

### 2. 代码可运行性（分级要求）

按代码复杂度分级要求，避免一刀切「全部必须可运行」：

| 场景 | 要求 |
|------|------|
| 简单、自包含（单 API 用法，数十行内可独立演示） | **必须完整可运行**：依赖给出、变量声明齐全、无语法逻辑错误 |
| 中间态（补少量 mock 数据/最小环境即可跑） | 优先**最小可运行**：显式标注 mock 与最小环境，能跑就不退化成伪代码 |
| 复杂、强依赖（需真实服务、SDK Key、大型已有项目上下文） | 允许**显式标注的高质量伪代码**：写清关键变量、数据结构与数据流向 |

严禁**未标注的「伪可运行」代码**——看起来能跑、实际缺依赖与上下文，比诚实标注的伪代码更有害。

✅ 正面示例（简单自包含 → 完整可运行）：

```js
const stage = new Konva.Stage({ container: 'root', width: 800, height: 600 });
const layer = new Konva.Layer();
layer.add(new Konva.Circle({ x: 100, y: 100, radius: 50, fill: 'red' }));
stage.add(layer);
layer.draw();
```

✅ 正面示例（复杂强依赖 → 诚实标注的高质量伪代码）：

```js
// 伪代码：消息队列消费流程，省略 Redis 连接与 SDK 初始化
async function consume() {
  const msg = await broker.dequeue('task-queue')  // 消息结构: {id, type, payload}
  const handler = handlers[msg.type]              // handlers 由各业务模块注册
  if (handler) await handler(msg.payload)
  else await defaultSink(msg)
}
```

❌ 反面示例（未标注的伪可运行代码）：

```js
circle.fill('red')  // circle 未声明、缺注册与绘制，照抄即错
```

### 3. 面试导向性

- 面试回答模板紧扣知识点，内容「拿来就能用」（即答即中的水平）
- 设置自问自答式深入追问（如「面试常问：为什么没有自动渲染？」）
- 覆盖面试常见的追问点（陷阱、对比、原理）

### 4. 知识覆盖度

- 核心 API 全部涉及
- 边缘情况有说明（如序列化不保留事件、图片异步加载）
- 常见踩坑点提醒到位
- 有进阶延伸（性能优化、设计模式）

### 5. 渐进式学习

- 各篇之间自然递进，每篇在前一篇基础上扩展能力
- 练习难度递增
- 实战整合篇串联前面所有知识点

### 6. 对比完整性

每篇文末（面试模板之前）至少包含「本技术 + ≥1 个同类方案 + 原生/基线方案」的三角对比（如 Konva vs fabric.js vs 原生 Canvas、Electron vs Tauri vs 原生开发）。对比要落到具体维度（性能、API 设计、适用场景、生态成熟度、迁移成本），而非只罗列名词。

## 可溯源原则（写作侧）

- API 名称、参数、返回值、边界行为等技术细节对照**官方文档**核实，不凭记忆书写
- 关键断言（版本号、弃用/移除声明、时间线）逐条核对：先确认当前日期，核实该版本是否已发布；「计划发布」的版本不得表述为「已生效」
- 在版本断言、API 用法、新特性处适当附官方文档/Release Notes 链接，让读者能核对与深挖、避免知识孤岛
- 来源分级：`官方域名文档 > GitHub releases/changelog > 官方博客 > 框架源码 > 社区最佳实践 > 个人经验`；警惕 SEO 镜像站

## 写作自查清单

发布前按优先级自查：

| 级别 | 检查项 |
|:--:|------|
| **P0 正确性** | 技术事实是否有官方来源；简单代码示例照抄能否运行；版本断言与当前日期是否一致；安全配置是否准确 |
| **P1 规范与结构** | 文件命名、头部元信息、绘图（Mermaid）是否符合约定；练习/对比/面试板块是否齐全；与其它文档有无矛盾（术语、版本号、结论） |
| **P2 小瑕疵** | 依赖与版本是否过旧；措辞、风格是否统一 |
