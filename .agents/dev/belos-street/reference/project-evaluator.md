# 项目综合水平评价（Project Evaluator）

> 一句话：一套「结构盘点 → 并行取证 → 交叉验证 → 锚定评分 → 五段报告」的仓库级质量评测流程，输出 10 分制评分表 + 关键证据 + 团队画像 + 行动优先级。触发场景：用户要求评价/评分/对比项目或代码库水平（如「评价项目水平」「代码质量评分」「项目对比评测」「团队水平点评」）。适用单仓库体检，也适用多仓库对比。

## 与代码级 Review 的分工

- 本篇评**仓库级系统性水平**（架构、工程化、文档、提交纪律、人力风险等仓库级事实）；
- 变更/文件级细粒度走 [code-review-dimensions](code-review-dimensions.md) 八维度清单——本篇维度 2/3/4（可维护性/类型纪律/安全）抽样取证时**直接复用该清单**，标准只定义一份，防漂移。

## 核心原则（方法论灵魂，违反即废）

1. **证据先行**：每个分数必须有 file:line 级证据支撑，禁止凭印象打分；取不到证的维度标注「待核实」并降权处理。
2. **评分锚定**：严格按下方标尺锚点打分，不自由发挥。
3. **公允性声明**：必须声明项目年龄/规模/人力的不对等影响；**代码评价 ≠ 个人考绩**，结论表述为「团队能力画像」。
4. **点面分离**：区分「点状精品」与「系统性水平」——「能人不少、治理为零」和「治理良好、覆盖不足」是两种完全不同的诊断，处方也不同。
5. **可执行收尾**：评测必须落到行动优先级（按风险×成本排序），没有行动建议的评测是空谈。

## 评测流程（五步）

### 第一步：结构盘点

根目录列表、构建文件（package.json / pom.xml / go.mod）、目录树、CI 配置、git log 概览。产出：技术栈事实清单。

### 第二步：并行取证

多仓库时**每仓库派一个 Explore 子代理并行执行**（单仓库可自己抽样）。子代理提示词模板：

```
你是代码评审专家。请对 <仓库路径>（<技术栈一句话>）做代码质量取证，目的是给团队 leader 一份客观评价。只做研究，不写代码。排除 node_modules/target/vendor 等构建产物。
请取证以下维度，每条都要给出具体文件路径和行号证据（引用关键代码片段）：
1. 分层与架构：抽读 2-3 个代表性入口层（controller/api handler）+ 对应实现层，看业务逻辑泄漏、事务边界、横切关注点处理
2. 代码坏味道：找最大 5 个源文件（行数），看 god class、超长方法、重复代码
3. 安全与健壮性：注入风险（SQL/命令拼接）、密码/加密处理（哈希算法强度）、异常吞噬、危险依赖用法
4. 测试质量：统计测试文件数 vs 主代码文件数，抽读 1-2 个测试看断言真实性（真断言还是形式主义）
5. 数据访问/API 层：ORM/封装用法是否地道，有无绕过框架的裸操作
6. 依赖健康：结合构建文件列 EOL/已知 CVE/停维护依赖
7. 提交历史：git log --oneline -30 看提交信息质量，git shortlog -sn 看贡献者结构与集中度
8. 工程化：CI 配置有无 test/lint 门禁，构建/校验脚本质量抽查
输出：按维度组织，每维度「证据 + 一句话评价（好/中/差）」，最后给总体印象段。控制在 900 字以内，用中文。
```

### 第三步：交叉验证

对子代理报告中的**可计数断言**（文件数、包数量、文件大小、出现次数）用 Grep/Shell 抽查复核，防幻觉；未复核的关键事实不进报告。

### 第四步：逐维评分

按下方标尺打分，每个维度写一句话评分依据（含证据指向）。

### 第五步：输出报告（固定五段，不得省略）

## 十个维度与评分标尺（10 分制）

**锚点**：9-10 优＝行业标杆水准｜7-8 良＝高于平均、短板明确可补｜5-6 中＝及格线、靠自觉维持｜3-4 差＝系统性失控、需制度干预｜0-2 极差＝完全空白或失控且无人意识到

**总分口径**：默认只输出各维度分，不强制加权总分；如需总分，必须先声明权重口径（如「安全 ×2」），且同一次对比内所有项目使用同一口径。

| # | 维度 | 取证要点 |
| --- | --- | --- |
| 1 | 架构与分层 | 入口层是否克制、事务/状态边界、横切关注点（鉴权/审计/日志）是否注解化或统一封装 |
| 2 | 代码可维护性 | 最大文件 Top5、超长方法、god class、模块拆分意识（细查复用 code-review-dimensions 清单） |
| 3 | 语言/类型纪律 | TS：strict 配置 + `: any`/`@ts-ignore` 计数；Java：命名/注解规范；有无绕过框架的裸操作 |
| 4 | 安全 | 注入、密码哈希强度（慢哈希?）、敏感加密设计、危险依赖用法、鉴权体系清晰度（细查复用 code-review-dimensions 安全维度） |
| 5 | 测试 | **双轴**：覆盖数量级（测试文件:主文件）× 断言真实性（抽读） |
| 6 | 依赖健康 | EOL 运行时、已知 CVE 版本、停维护库、双框架并存类设计债 |
| 7 | 工程化与 CI | lint/format/hooks/CI 门禁齐不齐；**关键判据：制度（文档）与机器兜底（CI/hooks）是否分离**——只立法不执法扣分 |
| 8 | 文档与协作 | 判据：真沉淀（含历史事故/真实路径/决策记录）还是模板空壳；文档是否可作运维资产 |
| 9 | 提交与版本纪律 | Conventional Commits 比例、change-id 关联、空泛消息/重复提交比例 |
| 10 | 人力风险（巴士因子） | 贡献者 commit 集中度（Top2 占比）、无人敢动的模块（god class 知识垄断）、中英文作者名重复记账 |

**取证命令速查**：坏味道＝列最大文件；类型纪律＝Grep count；安全＝Grep 拼接+定位哈希算法；测试＝计数+抽读；提交＝`git log --oneline -30` + `git shortlog -sn`；CI＝读 yml 找 test/lint stage。

## 输出格式（五段固定）

1. **总评分览表**：维度 × 两列得分 × 一句话依据（多项目时并排）
2. **关键证据**：每项目 3-5 条 file:line 引用，好坏证据都要有（只列坏的会失真）
3. **团队画像**：一句话定型，推荐句式「X 分的能力写了 Y 分的代码，被 Z 拖累」
4. **公允性说明**：规模/年龄不对等修正；「若按新写代码口径单独评」的修正段（多项目对比必给）
5. **行动优先级 Top5**：按 风险×成本 排序，标注每项对应哪个维度的失分

## 评分反模式（禁止）

- 禁止无证据打分、禁止「总体感觉 7 分」式整体分替代维度分
- 禁止把「代码老」等同「水平差」（必须做年龄修正）
- 禁止跳过公允性声明
- 禁止评测不含行动建议
- 禁止只列坏证据或只列好证据（必须双向）
- 禁止对个人点名定性（对代码点名、对团队画像）
